Opis systemu

Car Service to obiektowy, wielowątkowy system informatyczny działający w architekturze klient-serwer, wspierający codzienną pracę warsztatu samochodowego. System obsługuje pełny proces realizacji usług serwisowych: od założenia konta i rezerwacji terminu wizyty przez klienta, przez przyjęcie samochodu, utworzenie zlecenia, wydanie części z magazynu i wykonanie naprawy przez mechanika, aż po wystawienie faktury oraz rozliczenie zlecenia przez managera warsztatu.

Podstawowym obiektem w systemie jest zlecenie naprawy. Powstaje ono na podstawie potwierdzonej rezerwacji w momencie przyjęcia samochodu do warsztatu i dotyczy jednego pojazdu przypisanego do konkretnego klienta. Zlecenie naprawy zawiera opis zgłoszonej usterki, datę przyjęcia, przydzielonego mechanika, aktualny status oraz listę wykonanych napraw wraz z przypisanymi częściami zamiennymi. W trakcie obsługi zlecenie przechodzi przez kolejne statusy: przyjęte, w trakcie realizacji, oczekuje na części, oczekuje na akceptację kosztorysu, zakończone oraz rozliczone.

Pojazd w systemie opisany jest marką, modelem, rokiem produkcji, numerem VIN, numerem rejestracyjnym oraz aktualnym przebiegiem. Każdy pojazd jest przypisany do właściciela (klienta) i posiada swoją historię serwisową. W ramach pojedynczego zlecenia mechanik zamawia potrzebne części u magazyniera oraz rejestruje wykonane naprawy (czynności serwisowe, czas pracy i zużyte części). Jeżeli w trakcie diagnostyki lub pracy mechanik wykryje dodatkową usterkę, tworzy w systemie kosztorys dodatkowych prac, który klient może zaakceptować lub odrzucić przed kontynuowaniem naprawy.

Części zamienne przechowywane są w magazynie warsztatu i opisane nazwą, numerem katalogowym, producentem, ceną oraz aktualnym stanem magazynowym. Mechanik zgłasza zapotrzebowanie na części przypisane do konkretnego zlecenia naprawy, natomiast magazynier weryfikuje ich dostępność, wydaje je mechanikowi, a w razie braków zamawia części u dostawców i rejestruje przyjęcie dostaw do magazynu. Zamówienie części składa się z pozycji (część i ilość); te same pozycje opisują części użyte w naprawie i wycenione w kosztorysie. Zamówienie u dostawcy dotyczy jednej części i pamięta ilość już dostarczoną, dzięki czemu dostawa może być częściowa.

W systemie wyróżniono czterech użytkowników (aktorów): Klienta, Mechanika, Magazyniera oraz Managera warsztatu. Klient rejestruje swoje pojazdy, rezerwuje terminy wizyt, śledzi status naprawy oraz akceptuje ewentualne kosztorysy dodatkowych prac. Mechanik przegląda przydzielone mu zlecenia, zamawia części u magazyniera, rejestruje wykonane naprawy, zgłasza dodatkowe usterki oraz aktualizuje status zlecenia. Magazynier obsługuje zapotrzebowania na części od mechaników, sprawdza stany magazynowe, wydaje części, zamawia brakujący asortyment u dostawców oraz przyjmuje dostawy. Manager warsztatu potwierdza rezerwacje i tworzy zlecenia naprawy, przydziela je mechanikom, zarządza cennikiem usług, wystawia faktury za zrealizowane zlecenia oraz generuje raporty z pracy warsztatu. Manager warsztatu posiada również uprawnienia mechanika, dzięki czemu może nadzorować i wykonywać operacje warsztatowe.

Założenia niefunkcjonalne systemu obejmują pracę w architekturze klient-serwer z centralną bazą danych oraz obsługę wielu wątków po stronie serwera, co umożliwia jednoczesną, bezkonfliktową pracę wielu klientów i pracowników warsztatu w czasie rzeczywistym. System zapewnia kontrolę dostępu opartą na rolach po uwierzytelnieniu użytkownika, spójność danych podczas równoczesnej edycji zleceń i stanów magazynowych, czas odpowiedzi interfejsu poniżej 2 sekund dla standardowych operacji oraz przejrzysty, responsywny interfejs użytkownika dostosowany do komputerów stacjonarnych, tabletów warsztatowych i urządzeń mobilnych.

System description

Car Service is an object-oriented, multi-threaded information system operating in a client-server architecture that supports the daily operations of an automotive repair shop. The system covers the entire service process: from account creation and appointment booking by the client, through vehicle intake, repair order creation, spare parts issuance from the warehouse, and repair execution by the mechanic, up to invoice generation and order settlement by the workshop manager.

The core entity in the system is the repair order. It is created based on a confirmed appointment when a vehicle is accepted into the workshop and applies to a single vehicle assigned to a specific client. The repair order contains a description of the reported fault, acceptance date, assigned mechanic, current status, and a list of performed repairs along with assigned spare parts. During processing, the order transitions through successive statuses: accepted, in progress, waiting for parts, waiting for estimate approval, completed, and settled.

A vehicle in the system is described by its make, model, production year, VIN, registration number, and current mileage. Each vehicle is assigned to an owner (client) and has its own service history. Within a single repair order, the mechanic requests necessary parts from the storekeeper and records completed repairs (service activities, working time, and used parts). If the mechanic detects an additional fault during diagnostics or repair work, they create a cost estimate for additional work in the system, which the client can accept or reject before the repair continues.

Spare parts are stored in the workshop warehouse and are described by name, catalog number, manufacturer, price, and current stock level. The mechanic submits a part request linked to a specific repair order, while the storekeeper verifies availability, issues the parts to the mechanic, and in case of shortages, orders parts from suppliers and records incoming deliveries into the warehouse. A part request consists of items (a part and a quantity); the same items describe the parts used in a repair and priced in a cost estimate. A supplier order concerns a single part and keeps track of the quantity already delivered, so a delivery may be partial.

There are four users (actors) in the system: Client, Mechanic, Storekeeper, and Workshop Manager. The Client registers their vehicles, books appointments, tracks repair status, and approves cost estimates for additional work. The Mechanic views assigned repair orders, requests parts from the storekeeper, records performed repairs, reports additional faults, and updates the order status. The Storekeeper handles part requests from mechanics, checks stock levels, issues parts, orders missing items from suppliers, and receives deliveries. The Workshop Manager confirms appointments and creates repair orders, assigns them to mechanics, manages the service price list, issues invoices for completed orders, and generates workshop performance reports. The Workshop Manager also inherits the privileges of a mechanic, allowing them to supervise and perform workshop operations.

Non-functional requirements of the system include operating in a client-server architecture with a central database and multi-threaded server-side processing, enabling simultaneous, conflict-free work by multiple clients and workshop employees in real time. The system provides role-based access control after user authentication, data consistency during concurrent editing of orders and stock levels, an interface response time of under 2 seconds for standard operations, and a clear, responsive user interface adapted to desktop computers, workshop tablets, and mobile devices.

Słownik pojęć

  • Użytkownik Osoba posiadająca konto w systemie i logująca się do niego: klient, mechanik, magazynier lub manager warsztatu. Zakres dostępnych funkcji zależy od roli użytkownika.
  • Klient Właściciel pojazdu korzystający z usług warsztatu. Posiada konto w systemie, rejestruje swoje samochody, umawia wizyty, śledzi status zlecenia oraz decyduje o akceptacji kosztorysu dodatkowych napraw.
  • Mechanik Pracownik warsztatu realizujący naprawy pojazdów. Przegląda przydzielone mu zlecenia, zamawia części u magazyniera, wprowadza wykonane czynności serwisowe, zgłasza dodatkowe usterki i zmienia statusy zleceń.
  • Magazynier Pracownik odpowiedzialny za magazyn części zamiennych. Obsługuje zamówienia od mechaników, sprawdza dostępność części, wydaje je do zleceń, zamawia brakujące pozycje u dostawców i przyjmuje dostawy.
  • Manager warsztatu Kierownik zarządzający pracą warsztatu. Tworzy zlecenia naprawy na podstawie rezerwacji, przydziela je mechanikom, zarządza cennikiem usług, wystawia faktury oraz generuje raporty. Dziedziczy również uprawnienia mechanika.
  • Pojazd Samochód należący do klienta, opisany marką, modelem, rokiem produkcji, numerem VIN, numerem rejestracyjnym oraz przebiegiem. Posiada przypisaną historię serwisową.
  • Rezerwacja wizyty Zgłoszenie chęci oddania pojazdu do warsztatu w wybranym terminie wraz z wstępnym opisem usterki, składane przez klienta w systemie. Ma status: oczekuje na potwierdzenie, potwierdzona lub zrealizowana.
  • Zlecenie naprawy Główny obiekt w systemie tworzony przez managera warsztatu przy przyjęciu pojazdu. Skupia informacje o pojeździe, kliencie, przydzielonym mechaniku, statusie prac, wykonanych naprawach i naliczonych kosztach.
  • Status zlecenia Informacja określająca bieżący etap realizacji zlecenia naprawy (np. przyjęte, w trakcie realizacji, oczekuje na części, oczekuje na akceptację kosztorysu, zakończone, rozliczone).
  • Historia statusów Lista kolejnych zmian statusu zlecenia naprawy wraz z datą zmiany i komentarzem mechanika, dostępna dla klienta podczas śledzenia statusu zlecenia.
  • Naprawa Pojedyncza czynność serwisowa wykonana przez mechanika w ramach zlecenia naprawy, określająca rodzaj usługi, czas pracy oraz użyte części zamienne wraz z ich ilością.
  • Dodatkowa usterka Nieprzewidziana awaria wykryta przez mechanika podczas diagnostyki lub naprawy pojazdu, wykraczająca poza pierwotny zakres zlecenia.
  • Kosztorys Wycena usunięcia dodatkowej usterki (obejmująca koszt robocizny i części), która wymaga akceptacji klienta przed przystąpieniem do prac. Ma status: oczekujący, zaakceptowany lub odrzucony.
  • Część zamienna Element eksploatacyjny lub konstrukcyjny pojazdu przechowywany w magazynie warsztatu, opisany nazwą, numerem katalogowym, ceną oraz aktualnym stanem magazynowym.
  • Zamówienie części Wewnętrzne zapotrzebowanie na części zamienne składane przez mechanika u magazyniera w ramach realizowanego zlecenia naprawy. Składa się z pozycji części i ma status: złożone, oczekujące, gotowe do wydania, zrealizowane lub anulowane.
  • Pozycja części Część zamienna wraz z ilością. Występuje w zamówieniu części, w naprawie (części użyte) oraz w kosztorysie (części wyceniane).
  • Dostawa części Partia części zamiennych zamówiona u zewnętrznego dostawcy i przyjmowana na stan magazynu przez magazyniera.
  • Dostawca Zewnętrzna firma oferująca części zamienne, u której magazynier zamawia brakujące części. Dostawca może wymagać minimalnej ilości zamówienia.
  • Zamówienie u dostawcy Zamówienie brakującej części składane przez magazyniera u dostawcy, określające ilość, cenę i przewidywany termin dostawy. Ma status wysłane, do ponownej wysyłki, częściowo zrealizowane lub zrealizowane i pamięta ilość już dostarczoną.
  • Usługa serwisowa Pozycja cennika usług opisana nazwą, opisem, stawką za roboczogodzinę lub ceną stałą, szacowanym czasem wykonania oraz datą obowiązywania stawki.
  • Cennik usług Zbiór stawek za poszczególne usługi serwisowe i robociznę, zarządzany przez managera warsztatu i wykorzystywany do wyceny zleceń.
  • Faktura Dokument rozliczeniowy generowany przez managera warsztatu po zakończeniu zlecenia naprawy, podsumowujący koszt robocizny oraz zużytych części. Zawiera numer, datę wystawienia, formę płatności (gotówka, karta lub przelew) i opcjonalnie NIP klienta.
  • Raport Zestawienie statystyczne i finansowe generowane przez managera warsztatu, obejmujące m.in. liczbę zrealizowanych zleceń, zużycie części oraz przychody w wybranym okresie.

Dictionary

  • User A person who has an account in the system and logs in to it: a client, mechanic, storekeeper or workshop manager. The available functions depend on the user's role.
  • Client The vehicle owner using the workshop's services. Has an account in the system, registers their cars, books appointments, tracks order status, and decides on accepting cost estimates for additional repairs.
  • Mechanic A workshop employee performing vehicle repairs. Views assigned orders, requests parts from the storekeeper, enters completed service activities, reports additional faults, and updates order statuses.
  • Storekeeper An employee responsible for the spare parts warehouse. Handles part requests from mechanics, checks part availability, issues parts for orders, orders missing items from suppliers, and receives deliveries.
  • Workshop Manager A manager overseeing workshop operations. Creates repair orders based on appointments, assigns them to mechanics, manages the service price list, issues invoices, and generates reports. Also inherits mechanic privileges.
  • Vehicle A car belonging to a client, described by make, model, production year, VIN, registration number, and mileage. Has an assigned service history.
  • Appointment Booking A request to leave a vehicle at the workshop on a selected date along with an initial fault description, submitted by the client in the system. Its status is pending confirmation, confirmed or completed.
  • Repair Order The main entity in the system created by the workshop manager upon vehicle intake. Combines information about the vehicle, client, assigned mechanic, work status, performed repairs, and calculated costs.
  • Order Status Information defining the current stage of repair order execution (e.g., accepted, in progress, waiting for parts, waiting for estimate approval, completed, settled).
  • Status History The list of successive status changes of a repair order with the change date and the mechanic's comment, available to the client when tracking the order status.
  • Repair A single service activity performed by a mechanic within a repair order, specifying the service type, working time, and used spare parts with their quantities.
  • Additional Fault An unforeseen malfunction detected by the mechanic during vehicle diagnostics or repair, exceeding the original scope of the order.
  • Cost Estimate A valuation for fixing an additional fault (including labor and parts costs), which requires client approval before work begins. Its status is pending, accepted or rejected.
  • Spare Part A consumable or structural vehicle component stored in the workshop warehouse, described by name, catalog number, price, and current stock level.
  • Part Request An internal request for spare parts submitted by a mechanic to the storekeeper within an active repair order. It consists of part items and its status is pending, waiting, ready for issue, fulfilled or cancelled.
  • Part Item A spare part together with a quantity. It appears in a part request, in a repair (used parts) and in a cost estimate (priced parts).
  • Parts Delivery A batch of spare parts ordered from an external supplier and received into warehouse stock by the storekeeper.
  • Supplier An external company offering spare parts, from which the storekeeper orders missing parts. A supplier may require a minimum order quantity.
  • Supplier Order An order for a missing part placed by the storekeeper with a supplier, specifying the quantity, price and expected delivery date. Its status is sent, to resend, partially completed or completed, and it keeps track of the quantity already delivered.
  • Service Item A price list entry described by name, description, hourly labor rate or fixed price, estimated duration and the date from which the rate applies.
  • Service Price List A collection of rates for individual service activities and labor, managed by the workshop manager and used for order valuation.
  • Invoice A billing document generated by the workshop manager after completion of a repair order, summarizing the cost of labor and used parts. It contains a number, issue date, payment method (cash, card or transfer) and optionally the client's tax ID.
  • Report A statistical and financial summary generated by the workshop manager, covering the number of completed orders, parts usage, and revenue in a selected period.

Jako klient chcę zarezerwować termin wizyty w warsztacie w taki sposób, aby wybrać dogodną datę i opisać usterkę bez konieczności dzwonienia.

Jako klient chcę śledzić status zlecenia naprawy mojego pojazdu w taki sposób, aby wiedzieć, na jakim etapie są prace i kiedy auto będzie gotowe do odbioru.

Jako klient chcę akceptować lub odrzucać kosztorys dodatkowych prac w taki sposób, aby mieć pełną kontrolę nad końcowym kosztem naprawy.

Mechanik

Jako mechanik chcę przeglądać listę przydzielonych mi zleceń naprawy wraz z historią pojazdu w taki sposób, aby wiedzieć, którymi samochodami mam się zająć i jakie naprawy przechodziły wcześniej.

Jako mechanik chcę zamawiać potrzebne części zamienne u magazyniera w taki sposób, aby zostały one przygotowane i przypisane do realizowanego zlecenia naprawy.

Jako magazynier chcę sprawdzać dostępność i stan magazynowy części w taki sposób, aby szybko zweryfikować, czy dany element znajduje się w warsztacie.

Jako magazynier chcę rejestrować przyjęcie dostawy części do magazynu w taki sposób, aby zaktualizować stany magazynowe oraz katalog części w systemie.

Jako manager warsztatu chcę generować raporty z pracy warsztatu w taki sposób, aby monitorować przychody oraz liczbę zrealizowanych napraw.

User Stories (in english)

Client

As a client I want to create an account and log in to the system so that I can have remote access to workshop services and my orders.

As a client I want to add my vehicle to my account so that I do not have to provide detailed car information at every subsequent visit.

As a client I want to book an appointment at the workshop so that I can choose a convenient date and describe the fault without having to call.

As a client I want to track the status of my vehicle's repair order so that I know what stage the work is at and when the car will be ready for pickup.

As a client I want to accept or reject the cost estimate for additional work so that I have full control over the final repair cost.

Mechanic

As a mechanic I want to view the list of repair orders assigned to me along with the vehicle history so that I know which cars to work on and what repairs they have undergone previously.

As a mechanic I want to request necessary spare parts from the storekeeper so that they are prepared and assigned to the active repair order.

As a mechanic I want to enter completed repairs and working time into the system so that the order cost is automatically calculated.

As a mechanic I want to report an additional fault detected during work so that a cost estimate is generated for client approval before expanding the repair.

As a mechanic I want to change the status of the repair order so that the client and the workshop manager can see the current progress of work.

Storekeeper

As a storekeeper I want to view part requests submitted by mechanics so that I know which items I need to prepare for current orders.

As a storekeeper I want to check the availability and stock level of parts so that I can quickly verify whether a given item is in the workshop.

As a storekeeper I want to issue requested parts to the mechanic so that they are assigned to the order and the stock level is automatically reduced.

As a storekeeper I want to order missing spare parts from a supplier so that I can replenish stock shortages and enable the completion of repairs.

As a storekeeper I want to record the receipt of a parts delivery into the warehouse so that stock levels and the parts catalog are updated in the system.

Workshop Manager

As a workshop manager I want to confirm appointment bookings and create repair orders based on them so that vehicle intake into the service is formally registered.

As a workshop manager I want to assign repair orders to mechanics so that work in the workshop is evenly distributed.

As a workshop manager I want to manage the service price list so that cost estimates and invoices are calculated according to current rates.

As a workshop manager I want to issue an invoice for a completed repair order so that I can settle the payment with the client upon vehicle pickup.

As a workshop manager I want to generate workshop performance reports so that I can monitor revenue and the number of completed repairs.

Problem

W przypadku użycia „Zaakceptuj kosztorys dodatkowych prac” klient ogląda kosztorys (krok 2), wybiera opcję Akceptuj i potwierdza decyzję (kroki 3–5). W tym czasie mechanik może zmienić kosztorys, np. dodać usługę albo zmienić ilość części. Dlatego w kroku 6 system sprawdza, czy kosztorys nie został w międzyczasie zmieniony, a jeśli tak, wyświetla go ponownie (przepływ alternatywny 6, GOTO 2). Klient może zaakceptować tylko taki kosztorys, jaki faktycznie widział.

Żeby to sprawdzić, system musi zapamiętać kosztorys dokładnie w tej postaci, w jakiej został pokazany klientowi. Zapamiętanie samej referencji nic nie daje, bo wskazuje ten sam obiekt, który zmienia mechanik. Przepisywanie pól poza klasą CostEstimate jest podatne na błędy: kosztorys zawiera listę usług i listę pozycji części (PartItem). Kopia płytka dzieliłaby z oryginałem te same pozycje części, więc zmiana ilości przez mechanika zmieniłaby też zapamiętaną kopię i zmiana nie zostałaby wykryta.

Rozwiązanie

Prototyp pozwala tworzyć nowe obiekty przez klonowanie istniejącego obiektu, zamiast budować je od zera. Obiekt sam wie, jak utworzyć swoją kopię, więc kod, który z niej korzysta, nie musi znać jego budowy.

  • Prototype – klasa abstrakcyjna z metodą clone().
  • CostEstimate i PartItem – prototypy konkretne (klasy z diagramu klas). Kopię tworzą prywatne konstruktory kopiujące wywoływane w clone().
  • EstimateReview – klient prototypu. Przy wyświetleniu kosztorysu (display()) zapamiętuje jego klon, a przy potwierdzeniu (confirmAcceptance()) porównuje klon z aktualnym kosztorysem metodą hasSameContentAs(). Jeśli treść się różni, akceptacja nie jest zapisywana i kosztorys trzeba wyświetlić ponownie.

Kopia jest głęboka tam, gdzie wymaga tego diagram klas. Pozycje części należą do kosztorysu (kompozycja CostEstimate–PartItem), więc każda jest klonowana. Usługi pochodzą z cennika (asocjacja), dlatego kopia dostaje nową listę z tymi samymi obiektami ServiceItem. Kopia zachowuje identyfikator, bo jest obrazem tego samego kosztorysu, a nie nowym kosztorysem. Tak jak w materiałach, clone() nie korzysta z mechanizmu Cloneable, tylko jawnie wywołuje konstruktor kopiujący.

Wzorzec pasuje do problemu, bo w chwili wyświetlenia potrzebna jest wierna i niezależna kopia obiektu o złożonej strukturze. Klasy ServiceItem i SparePart są w kodzie uproszczone do pól potrzebnych w kosztorysie.

// Prototyp abstrakcyjny - obiekt, który potrafi utworzyć swoją kopię
public abstract class Prototype {

    public abstract Prototype clone();
}

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

// Kosztorys dodatkowych prac - prototyp konkretny
public class CostEstimate extends Prototype {
    private static int nextId = 1;

    private final int id;
    private final String faultDescription;
    private final List<ServiceItem> services;
    private final List<PartItem> parts;
    private EstimateStatus status;

    public CostEstimate(String faultDescription) {
        this.id = nextId++;
        this.faultDescription = faultDescription;
        this.services = new ArrayList<>();
        this.parts = new ArrayList<>();
        this.status = EstimateStatus.PENDING;
    }

    // Konstruktor kopiujący - używa go metoda clone()
    private CostEstimate(CostEstimate other) {
        this.id = other.id;
        this.faultDescription = other.faultDescription;
        // Nowa lista, ale te same usługi - usługi należą do cennika, a nie do kosztorysu
        this.services = new ArrayList<>(other.services);
        // KOPIA GŁĘBOKA: pozycje części należą do kosztorysu (kompozycja), więc każda jest klonowana
        this.parts = new ArrayList<>();
        for (PartItem item : other.parts) {
            this.parts.add(item.clone());
        }
        this.status = other.status;
    }

    @Override
    public CostEstimate clone() {
        return new CostEstimate(this);
    }

    public void addService(ServiceItem service) {
        services.add(service);
    }

    public void addPart(SparePart part, int quantity) {
        parts.add(new PartItem(part, quantity));
    }

    // Koszt robocizny liczony według cennika dla szacowanego czasu wykonania usług
    public double calculateLaborCost() {
        double cost = 0;
        for (ServiceItem service : services) {
            cost += service.calculatePrice(service.getEstimatedTime());
        }
        return cost;
    }

    public double calculatePartsCost() {
        double cost = 0;
        for (PartItem item : parts) {
            cost += item.calculateCost();
        }
        return cost;
    }

    public double calculateTotal() {
        return calculateLaborCost() + calculatePartsCost();
    }

    public void accept() {
        checkPending();
        status = EstimateStatus.ACCEPTED;
    }

    public void reject() {
        checkPending();
        status = EstimateStatus.REJECTED;
    }

    private void checkPending() {
        if (status != EstimateStatus.PENDING) {
            throw new IllegalStateException("Decyzja o kosztorysie została już zapisana");
        }
    }

    // Porównanie treści dwóch kosztorysów (opis usterki, usługi, części i ich ilości)
    public boolean hasSameContentAs(CostEstimate other) {
        if (id != other.id
                || !faultDescription.equals(other.faultDescription)
                || !services.equals(other.services)
                || parts.size() != other.parts.size()) {
            return false;
        }
        for (int i = 0; i < parts.size(); i++) {
            if (!parts.get(i).hasSameContentAs(other.parts.get(i))) {
                return false;
            }
        }
        return true;
    }

    public List<ServiceItem> getServices() { return Collections.unmodifiableList(services); }

    public List<PartItem> getParts() { return Collections.unmodifiableList(parts); }

    public EstimateStatus getStatus() { return status; }
}

// Pozycja "część + ilość" - prototyp konkretny
public class PartItem extends Prototype {
    private final SparePart part;
    private int quantity;

    public PartItem(SparePart part, int quantity) {
        this.part = part;
        this.quantity = quantity;
    }

    // Konstruktor kopiujący - używa go metoda clone()
    private PartItem(PartItem other) {
        this.part = other.part;          // ta sama część z katalogu
        this.quantity = other.quantity;
    }

    @Override
    public PartItem clone() {
        return new PartItem(this);
    }

    // Mechanik zmniejsza ilość części w kosztorysie
    public void reduceQuantity(int quantity) {
        if (quantity <= 0 || quantity >= this.quantity) {
            throw new IllegalArgumentException("Niepoprawna ilość do usunięcia: " + quantity);
        }
        this.quantity -= quantity;
    }

    public double calculateCost() {
        return part.getPrice() * quantity;
    }

    public boolean hasSameContentAs(PartItem other) {
        return part == other.part && quantity == other.quantity;
    }

    public SparePart getPart() { return part; }

    public int getQuantity() { return quantity; }
}

// Przegląd kosztorysu przez klienta (przypadek użycia "Zaakceptuj kosztorys dodatkowych prac")
public class EstimateReview {
    private final CostEstimate estimate;   // kosztorys zapisany w zleceniu - mechanik może go zmienić
    private CostEstimate displayedCopy;    // kopia kosztorysu w postaci pokazanej klientowi

    public EstimateReview(CostEstimate estimate) {
        this.estimate = estimate;
    }

    // Krok 2: system wyświetla kosztorys i zapamiętuje jego kopię
    public CostEstimate display() {
        displayedCopy = estimate.clone();
        return displayedCopy;
    }

    // Kroki 5-7: klient potwierdza akceptację, system sprawdza, czy kosztorys się nie zmienił
    public boolean confirmAcceptance() {
        if (displayedCopy == null) {
            throw new IllegalStateException("Kosztorys nie został wyświetlony klientowi");
        }
        if (!estimate.hasSameContentAs(displayedCopy)) {
            // Przepływ alternatywny 6: kosztorys zmieniony przez mechanika - trzeba go wyświetlić ponownie (GOTO 2)
            return false;
        }
        estimate.accept();
        return true;
    }
}

public class ServiceItem {
    private final String name;
    private final double rate;
    private final boolean fixedPrice;
    private double estimatedTime;

    public ServiceItem(String name, double rate, boolean fixedPrice) {
        this.name = name;
        this.rate = rate;
        this.fixedPrice = fixedPrice;
    }

    public double getEstimatedTime() { return estimatedTime; }

    // Cena stała albo stawka za roboczogodzinę razy czas pracy
    public double calculatePrice(double workTime) {
        return fixedPrice ? rate : rate * workTime;
    }
}

import java.util.List;
import java.util.Map;

// Budowniczy zamówienia części (przypadek użycia "Zamów części u magazyniera")
public class PartRequestBuilder {
    private final RepairOrder repairOrder;
    private final List<PartRequest> existingRequests;   // zamówienia już złożone do zleceń
    private final Map<SparePart, Integer> selectedParts = new LinkedHashMap<>();

    public PartRequestBuilder(RepairOrder repairOrder, List<PartRequest> existingRequests) {
        this.repairOrder = repairOrder;
        this.existingRequests = existingRequests;
    }

    // Krok 7: mechanik wybiera część z katalogu i podaje ilość.
    // Ponowny wybór tej samej części zmienia jej ilość.
    public PartRequestBuilder selectPart(SparePart part, int quantity) {
        selectedParts.put(part, quantity);
        return this;
    }

    // Poprawa zamówienia po błędzie walidacji (GOTO 6) - rezygnacja z wybranej części
    public PartRequestBuilder removePart(SparePart part) {
        selectedParts.remove(part);
        return this;
    }

    // Kroki 8-10: wysłanie zamówienia, walidacja i utworzenie zamówienia przypisanego do zlecenia
    public PartRequest build() {
        validate();
        PartRequest request = new PartRequest(repairOrder);
        for (Map.Entry<SparePart, Integer> entry : selectedParts.entrySet()) {
            request.addItem(entry.getKey(), entry.getValue());
        }
        return request;
    }

    // Krok 9 i przepływy alternatywne z kroku 9
    private void validate() {
        if (selectedParts.isEmpty()) {
            throw new IllegalStateException("Nie wybrano żadnej części");
        }
        for (Map.Entry<SparePart, Integer> entry : selectedParts.entrySet()) {
            SparePart part = entry.getKey();
            if (entry.getValue() <= 0) {
                throw new IllegalStateException(
                        "Niepoprawna ilość części " + part.getName() + ": " + entry.getValue());
            }
            if (isAlreadyOrdered(part)) {
                throw new IllegalStateException("Część " + part.getName()
                        + " została już zamówiona do tego zlecenia i nie została jeszcze wydana");
            }
        }
    }

    private boolean isAlreadyOrdered(SparePart part) {
        for (PartRequest request : existingRequests) {
            if (request.getRepairOrder() == repairOrder && request.isNotIssued() && request.containsPart(part)) {
                return true;
            }
        }
        return false;
    }
}

import java.util.LinkedHashMap;
import java.util.Map;

// Fabryka z metodą fabrykującą - decyduje, jaki rodzaj wydania utworzyć
public final class PartIssueFactory {

    private PartIssueFactory() {
    }

    // Krok 6: na podstawie dostępności zamówionych części tworzy odpowiedni rodzaj wydania
    public static PartIssue createIssue(PartRequest request) {
        Map<PartItem, Integer> missingQuantities = new LinkedHashMap<>();
        for (PartItem item : request.getItems()) {
            int available = item.getPart().getAvailableQuantity();
            if (available <= 0) {
                return new WaitingIssue(request);   // część niedostępna w magazynie
            }
            if (available < item.getQuantity()) {
                missingQuantities.put(item, item.getQuantity() - available);
            }
        }
        if (missingQuantities.isEmpty()) {
            return new FullIssue(request);
        }
        return new PartialIssue(request, missingQuantities);
    }
}

// Produkt abstrakcyjny - sposób wydania części dla zamówienia
public abstract class PartIssue {
    protected final PartRequest request;

    protected PartIssue(PartRequest request) {
        this.request = request;
    }

    // Krok 7: treść podsumowania wydania pokazywana magazynierowi
    public abstract String getSummary();

    // Skutki wydania w systemie (wywoływane po potwierdzeniu przez magazyniera)
    public abstract void execute();

    // Przepływ alternatywny 9: zlecenie zostało w międzyczasie zakończone lub rozliczone
    protected boolean cancelIfOrderClosed() {
        RepairOrderStatus orderStatus = request.getRepairOrder().getStatus();
        if (orderStatus == RepairOrderStatus.COMPLETED || orderStatus == RepairOrderStatus.SETTLED) {
            request.cancel();   // stan magazynowy pozostaje bez zmian
            return true;
        }
        return false;
    }
}

// Produkt konkretny - wydanie dostępnej ilości, brakująca ilość jest usuwana z zamówienia
public class PartialIssue extends PartIssue {
    private final Map<PartItem, Integer> missingQuantities;

    PartialIssue(PartRequest request, Map<PartItem, Integer> missingQuantities) {
        super(request);
        this.missingQuantities = missingQuantities;
    }

    @Override
    public String getSummary() {
        StringBuilder summary = new StringBuilder("Wydanie częściowe:");
        for (Map.Entry<PartItem, Integer> entry : missingQuantities.entrySet()) {
            PartItem item = entry.getKey();
            summary.append(" ").append(item.getPart().getName())
                    .append(" - brakuje ").append(entry.getValue()).append(" szt.;");
        }
        return summary.append(" brakująca ilość zostanie usunięta z zamówienia,")
                .append(" mechanik musi zamówić ją ponownie").toString();
    }

    @Override
    public void execute() {
        if (cancelIfOrderClosed()) {
            return;
        }
        for (Map.Entry<PartItem, Integer> entry : missingQuantities.entrySet()) {
            entry.getKey().reduceQuantity(entry.getValue());
        }
        for (PartItem item : request.getItems()) {
            item.getPart().decreaseStock(item.getQuantity());
        }
        request.markFulfilled();
    }
}

Problem

Z cennika usług korzysta wiele przypadków użycia. Manager dodaje do niego usługi („Dodaj usługę do cennika”), mechanik wybiera z niego usługi w formularzu naprawy („Wprowadź wykonaną naprawę”) i w zgłoszeniu dodatkowej usterki, na podstawie stawek z cennika wyliczane są kosztorysy („Zgłoś dodatkową usterkę”) i faktury („Wystaw fakturę”). Warunek końcowy przypadku użycia „Dodaj usługę do cennika” mówi, że nowa stawka jest stosowana przy wyliczaniu kosztorysów i faktur.

W warsztacie obowiązuje jeden cennik. Gdyby każdy serwis tworzył własny obiekt PriceList, usługa dodana przez managera nie byłaby widoczna w formularzu mechanika, a kosztorys i faktura za te same prace mogłyby zostać policzone według różnych stawek. Z cennika korzysta jednocześnie wielu użytkowników, więc jego utworzenie i zmiany muszą być bezpieczne przy pracy wielu wątków. Wzorzec nie dotyczy tu sposobu przechowywania danych, tylko reguły biznesowej: w całym systemie obowiązuje jeden cennik z jednolitymi stawkami.

Rozwiązanie

Singleton zapewnia, że klasa ma tylko jedną instancję, i daje pojedynczy punkt dostępu do niej.

  • PriceList ma prywatny konstruktor i statyczne pole instance. Jedyną instancję zwraca statyczna metoda getInstance(). Synchronizacja z podwójnym sprawdzeniem i słowo volatile zapewniają jedną instancję także przy wielu wątkach.
  • W odróżnieniu od przykładu z materiałów cennik się zmienia, bo manager dodaje usługi. Dlatego metody addService(), findService() i getServices() są synchronizowane, a getServices() zwraca niemodyfikowalną kopię listy.
  • addService() realizuje krok 8: zapisuje usługę z datą obowiązywania stawki albo zwraca false, gdy usługa o tej nazwie już istnieje (przepływ alternatywny 7). Pozostałe błędy z kroku 7, czyli brak nazwy i stawkę zerową lub ujemną, odrzuca konstruktor ServiceItem.
  • BillingServiceImpl – klient Singletona. Jego pole priceList (asocjacja „zarządza” z diagramu klas) wskazuje jedyną instancję cennika, więc każdy obiekt serwisu korzysta z tego samego cennika. Dlatego na diagramie wzorca liczność po stronie serwisu wynosi 0..*: wiele obiektów serwisu wskazuje jeden cennik.

Wzorzec pasuje do problemu, bo cennik musi istnieć w systemie dokładnie raz, a dostęp do niego jest potrzebny w wielu miejscach.

import java.time.LocalDate;
import java.util.ArrayList;
import java.util.List;

// Cennik usług warsztatu - Singleton
public final class PriceList {
    private static volatile PriceList instance;

    private final List<ServiceItem> services = new ArrayList<>();

    // Prywatny konstruktor - cennika nie można utworzyć spoza klasy
    private PriceList() {
    }

    public static PriceList getInstance() {
        if (instance == null) {
            synchronized (PriceList.class) {
                if (instance == null) {
                    instance = new PriceList();
                }
            }
        }
        return instance;
    }

    // Krok 8 przypadku użycia "Dodaj usługę do cennika".
    // Zwraca false, gdy usługa o tej nazwie już istnieje (przepływ alternatywny 7).
    public synchronized boolean addService(ServiceItem service) {
        if (findService(service.getName()) != null) {
            return false;
        }
        service.setValidFrom(LocalDate.now());
        services.add(service);
        return true;
    }

    // Zwraca usługę o podanej nazwie albo null, gdy takiej usługi nie ma w cenniku
    public synchronized ServiceItem findService(String name) {
        for (ServiceItem service : services) {
            if (service.getName().equalsIgnoreCase(name.trim())) {
                return service;
            }
        }
        return null;
    }

    // Lista usług do formularza naprawy, kosztorysu i faktury (tylko do odczytu)
    public synchronized List<ServiceItem> getServices() {
        return List.copyOf(services);
    }
}

public class ServiceItem {
    private final String name;
    private String description;
    private final double rate;           // stawka za roboczogodzinę albo cena stała
    private final boolean fixedPrice;
    private double estimatedTime;
    private LocalDate validFrom;

    public ServiceItem(String name, double rate, boolean fixedPrice) {
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("Nazwa usługi jest wymagana");
        }
        if (rate <= 0) {
            throw new IllegalArgumentException("Stawka musi być dodatnia (podano: " + rate + ")");
        }
        this.name = name.trim();
        this.rate = rate;
        this.fixedPrice = fixedPrice;
    }

    public double calculatePrice(double workTime) {
        return fixedPrice ? rate : rate * workTime;
    }

    // Datę obowiązywania stawki ustawia cennik w chwili dodania usługi
    void setValidFrom(LocalDate validFrom) { this.validFrom = validFrom; }

    public void setDescription(String description) { this.description = description; }

    public void setEstimatedTime(double estimatedTime) { this.estimatedTime = estimatedTime; }

    public String getName() { return name; }

    public String getDescription() { return description; }

    public double getEstimatedTime() { return estimatedTime; }

    public LocalDate getValidFrom() { return validFrom; }
}
